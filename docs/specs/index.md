# Specifications (SPDD)

VIMSEO features are specified with **Structured-Prompt-Driven Development** (SPDD).
Each feature is described by a *REASONS canvas*: a structured prompt versioned with the
code, reviewed like the code, and kept in sync with it. The canvases state *how* a
feature satisfies the [requirements](../requirements/index.md).

The canvases live in `spdd/prompt/` at the root of the repository. The SPDD commands of
Claude Code are in `.claude/commands/spdd-*.md`. They are generated by
[OpenSPDD](https://github.com/gszhangwei/open-spdd) and committed, so there is nothing
to install to use them. Only regenerating them needs the `openspdd` CLI
(`openspdd generate --all -t claude-code --force`).

## The commands

| Command | Input | Output |
|---|---|---|
| `/spdd-analysis` | a need (text, `@issue.md`) | an analysis: domain concepts, strategy, risks |
| `/spdd-reasons-canvas` | a need or an analysis, `@` files | a canvas in `spdd/prompt/` |
| `/spdd-prompt-update` | a canvas + a new need | the updated canvas |
| `/spdd-generate` | a canvas | the code implementing its *Operations* |
| `/spdd-sync` | a canvas | the canvas updated from the code |

Always add `@docs/specs/index.md` to `/spdd-analysis`, `/spdd-reasons-canvas` and
`/spdd-prompt-update`: this page holds the VIMSEO conventions below. They take
precedence over the generic (Java-flavoured) guidance of the commands.

## Workflows

### A. Retro-specify existing code

Used once per feature developed without a canvas, e.g. the branch
`feat/result-visualization`.

1. Generate the canvas from the code:

    ```text
    /spdd-reasons-canvas SPEC-NNN retro-specification of the existing code, do not
    change the code. Commits: <subjects of the commits>.
    @src/vimseo/<key module>.py @src/vimseo/<other key module>.py
    @docs/specs/index.md
    ```

    Answer **no** when the command offers to implement: the code exists.

2. Check the canvas against `git show <sha>` of each commit. Add the front matter
   (`status: Retro`, `requirements`, `commits`) and the *Open questions* section.
3. Run `/spdd-sync spdd/prompt/<canvas>.md` to align the canvas with the final state of
   the code.
4. Open a pull request with the canvas only. The reviewers comment on the canvas, not on
   the code.

### B. Iterate on a feature after a review

This is the main use with colleagues.

1. A review comment changes the need: run
   `/spdd-prompt-update spdd/prompt/<canvas>.md <the new need> @docs/specs/index.md`.
2. Commit the canvas. The reviewers read its diff: it is short, and it says what
   will change and why.
3. Run `/spdd-generate spdd/prompt/<canvas>.md` to implement the changed *Operations*.
4. Run the tests (`pytest`, `tox -e core-py312`) and commit the code in the same pull
   request.
5. If the code was then changed by hand, run `/spdd-sync spdd/prompt/<canvas>.md`
   before merging.

### C. Develop a new feature

1. `/spdd-analysis <need or @issue.md> @docs/requirements/ @docs/specs/index.md`.
   Add the new requirements to `docs/requirements/`, as `Proposed`.
2. `/spdd-reasons-canvas @<analysis> @docs/specs/index.md`. Set the next `SPEC-NNN`
   and `status: Draft`.
3. Review the canvas in a pull request (`status: Reviewed`).
4. Follow B.3 to B.5. Set `status: Implemented` when the pull request is merged.

### Rules

- **The canvas changes before the code** (`/spdd-prompt-update`, then `/spdd-generate`).
  When the code changed first, `/spdd-sync` before merging.
- A pull request changing code covered by a canvas contains the diff of that canvas.
- A canvas is never deleted: a replaced canvas gets `status: Superseded` and the
  identifier of its successor.

## VIMSEO conventions for the canvases

### File name

`SPEC-NNN-{YYYYMMDDHHmm}-[{Action}]-{scope}-{description}.md`, the OpenSPDD
convention with `SPEC-NNN` in place of the ticket key. `Action` is `Feat`, `Fix`,
`Refactor`, `Test` or `Docs`. `scope` is a VIMSEO area: `core`, `tools`, `results`,
`storage`, `serialization`, `workflow`, `cli`, `dashboards`.

### Front matter

The commands do not write it; add it after generating the canvas:

```yaml
---
id: SPEC-NNN
title: <feature>
status: Draft | Reviewed | Implemented | Retro | Superseded
requirements: [REQ-XXX-NNN, ...]
depends_on: [SPEC-NNN, ...]
commits: [<sha>, ...]        # once implemented
owner: <name>
---
```

### Sections

The seven REASONS sections (Requirements, Entities, Approach, Structure, Operations,
Norms, Safeguards), then **Open questions**: the points the reviewers have to decide.

Adapt the generic guidance of the commands to VIMSEO:

- *Entities*: the VIMSEO and GEMSEO classes (models, tools, settings, results,
  archives), not DTOs.
- *Structure*: the VIMSEO layers: `core` (models), `tools`, `storage_management`,
  `io`/`utilities`, `workflow`, `dashboards`. No controller, service or repository layers.
- *Operations*: one operation is small enough for one prompt and one conventional commit.
- *Safeguards*: list every breaking change (a `!` commit) with its migration path,
  and the tests which must pass.
- Approach: say which alternatives were rejected, and why.

### Norms shared by all canvases

1. VIMSEO models are GEMSEO `Discipline` subclasses; reuse GEMSEO before writing new
   code.
2. Settings and inputs are Pydantic models deriving from
   `vimseo.tools.base_settings.BaseSettings` (`extra="forbid"`).
3. Anything shipped by an extra (`dashboard`, `mlflow`, `mesh`, `jax`) is imported
   with `import_optional()` from `vimseo.utilities.optional_dependencies`, never at the
   top of a module.
4. Errors are standard Python exceptions (`ValueError`, `TypeError`, `KeyError`, ...)
   with a message saying what is wrong and what to do. There is no global exception
   handler.
5. Logging uses `logging.getLogger(__name__)`.
6. Docstrings follow the Google style used in the code (`Args:`, `Returns:`,
   `Raises:`), and every public object has one.
7. Tests mirror the source layout under `tests/` and carry a speed marker (`fast`,
   `medium_slow`, `slow`, `very_slow`).
8. Code is formatted and linted with `ruff`; commits follow Conventional Commits.
