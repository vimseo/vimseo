    RFC — A material forces its component to use a JSONGrammar¶

    Status of this document: proposal, checked against the codebase as of 2026-08-31.

    1. Diagnosis¶

    A BaseComponent that receives a material grammar must use a JSONGrammar. Nothing in the codebase states this, and neither of the two ways it breaks says so either: one raises a GEMSEO AttributeError that never mentions materials, the other silently produces an unbounded input space.

    The coupling is one line — base_component.py:91:

    if material_grammar_file != "":
    # Strict mode:
    self.input_grammar.update_from_file(material_grammar_file)

    update_from_file is declared only on JSONGrammar, under an explicit comment marking it as non-standard API (gemseo/core/grammars/json_grammar.py:299,301):

        # API not in the base class.

    def update_from_file(self, path: str | Path, merge: bool = False) -> None:

    Audited against the installed GEMSEO, over the four values of GrammarType (gemseo/core/grammars/factory.py:131-137):

    default_grammar_type update_from_file Result at base_component.py:91
    "JSONGrammar" yes works
    "SimpleGrammar" no AttributeError
    "SimplerGrammar" no AttributeError
    "PydanticGrammar" no AttributeError

    The default is correct — BaseComponent.default_grammar_type = Discipline.GrammarType.JSON (base_component.py:55) — so the trap only springs when a subclass overrides it. Which is not an exotic thing to do: SimpleGrammar is used deliberately at test_model_composition.py:38 and plot_041_post_processing_patch.py:55, and SimplerGrammar at workflow_step.py:141. Those are post-processors and workflow steps, none of which carries a material — which is precisely why the rule has never been hit and never been written down. The rule is "a simple grammar or a material", not "simple grammars are forbidden".

    1.1 Why this is intrinsic, not an API gap¶

    The obvious reading is that update_from_file is simply missing from BaseGrammar and someone should add it. It is not. A SimpleGrammar is a name→type map — __getitem__ returns type | None (simple_grammar.py:79) and _update_from_names maps every name to ndarray (simple_grammar.py:111-123). It has no slot for anything else.

    A material grammar is not a type map. Every property in plane_orthotropic_ply_grammar.json carries a range and a description:

    "nu12": {
  "description": "[Stiffness] Major Poisson's ratio, in-plane, direction 1-2 {{-}}",
  "items": { "maximum": 0.5, "minimum": 0.0, "type": "number" },
  "type": "array"
}

    and load_input_bounds reads those keywords straight off the JSON schema (json_grammar_utils.py:62-84):

    properties = grammar.schema["properties"]
...
lower_bound = properties[key]["items"].get("minimum")

    grammar.schema exists only on JSONGrammar. So the constraint is not "one method is missing", it is "the payload has no representation in the target". Adding update_from_file to SimpleGrammar would parse the file and throw away everything except the names.

    1.2 Only the schema half is JSON-bound¶

    Worth stating precisely, because it explains why a half-working fallback is tempting. The material contributes to a component through two independent paths (base_component.py:77-97):

    • material_grammar_file → input_grammar — types, bounds, descriptions, required names. JSON-only, per §1.1.
    • material → default_input_data, via material.get_values_as_dict() (material.py:249-258). This is a plain dict[str, ndarray] update and works with any grammar type.

    So under a SimpleGrammar the nominal values would still arrive; only validation and bounds would be lost. Silently. See §3.

    1.3 Second symptom — the bounds fallback nobody is told about¶

    The same root cause surfaces again, one level up, at base_integrated_model.py:334-345:

    if isinstance(self._chain.disciplines[0].input_grammar, JSONGrammar):
    self.lower_bounds, self.upper_bounds, self.input_space = load_input_bounds(
        self._chain.disciplines[0].input_grammar
    )
else:
    self.input_space = {}
    self.lower_bounds = {}
    self.upper_bounds = {}
    for name in self._chain.disciplines[0].input_grammar.names:
        self.lower_bounds[name] = [-inf]
        self.upper_bounds[name] = [inf]
        self.input_space[name] = [-inf, inf]

    No log, no warning. If the first component of the chain is not a JSONGrammar, every bound on the model becomes infinite — including the material bounds that the grammar file existed to carry. input_space, lower_bounds and upper_bounds are what the DOE, calibration, sensitivity and design-value tools sample from, so the failure is not a crash but a study that silently sweeps nu12 outside [0, 0.5].

    This is the more dangerous of the two symptoms, and it is the one an AttributeError fix must not accidentally open the door to.

    Scope check: today this else branch is not reachable from the composition path. ModelComposition puts a DisciplineWrapperComponent first (model_composition.py:53) and that component adopts the wrapped model's grammar object (discipline_wrapper_component.py:43), which for an IntegratedModel is a JSONGrammar (base_integrated_model.py:224). The SimpleGrammar post-processors of test_model_composition.py and plot_041 sit at index 1. The branch is dead code that becomes live the moment someone writes a non-JSON first component.

    1.4 The tan_oht case¶

    Both components already comply, explicitly:

    grammar type material grammar passed
    TanRun_Tension tan_oht.py:118 tan_oht.py:351
    PostFieldExtraction tan_oht.py:223 tan_oht.py:357

    Both set default_grammar_type = "JSONGrammar" — restating the inherited default, with no comment explaining that here it is load-bearing rather than decorative. Change either line to "SimpleGrammar" and the model stops constructing, with an error naming neither the material nor the grammar file.

    The same silence applies to PreRunPostModel, which hands _MATERIAL_GRAMMAR_FILE to its pre- and run-processors (pre_run_post_model.py:100,117) without any statement of what those components must be.

    One stale docstring to correct while we are here — tan_oht.py:112, on TanRun_Tension:

        """An Open Hole Tension model based on Tan theory (#open-hole-plate-model-tan-model).

    No grammar is defined for the material (and thus no bounds).
    """

    A material grammar is defined for it, at line 351, and it does carry bounds. The docstring describes a state of the code that no longer holds and points the reader in exactly the wrong direction on the question this RFC is about.

    2. Proposal¶

    Both, not either — they reach different people at different moments. The documentation reaches someone writing a new component; the error reaches someone who did not read it.

    2.1 Fail fast in BaseComponent.__init__¶

    Guard the call at base_component.py:91:

    if material_grammar_file != "":
    if not isinstance(self.input_grammar, JSONGrammar):
        msg = (
            f"Component {type(self).__name__} uses a "
            f"{type(self.input_grammar).__name__}, but a material grammar "
            f"({material_grammar_file}) can only be loaded into a JSONGrammar: "
            f"the property bounds and descriptions it carries have no "
            f"representation in a {type(self.input_grammar).__name__}. "
            f"Either set default_grammar_type = Discipline.GrammarType.JSON on "
            f"{type(self).__name__}, or construct the component without "
            f"material_grammar_file."
        )
        raise TypeError(msg)
    self.input_grammar.update_from_file(material_grammar_file)

    Test the instance, not the default_grammar_type class attribute: the instance is what GEMSEO actually built, and it is what Discipline itself inspects to report a grammar type (gemseo/core/discipline/io.py:118-120). A subclass that replaces self.input_grammar outright — DisciplineWrapperComponent does exactly that — would defeat an attribute-based check.

    TypeError rather than ValueError: the argument is well-formed, the receiver is of the wrong type.

    2.2 Warn on the silent path¶

    In the else branch at base_integrated_model.py:338, before filling the dictionaries with infinities:

    LOGGER.warning(
    "The input grammar of component %s is a %s, not a JSONGrammar: no input "
    "bounds can be read from it, so all bounds of model %s fall back to "
    "(-inf, inf). Any design or parameter space built from this model will be "
    "unbounded.",
    self._chain.disciplines[0].name,
    type(self._chain.disciplines[0].input_grammar).__name__,
    self.name,
)

    LOGGER is already defined in the module. This is deliberately a warning and not an error: an unbounded model is a legitimate configuration for a component that has no material and no declared ranges (§1.3 shows the branch exists for that case). What is not legitimate is arriving there without being told.

    2.3 Document the constraint¶

    Two places, aimed at the person writing a new component.

    In docs/how_to/model_integration.md, after line 71 ("The input grammar and default input data are automatically filled with the material properties"). The author comment already sitting at lines 55-57 — "It is weird that we talk about material grammar without before mentionning model/components grammar" — marks this as the known gap; the constraint is the missing sentence:

    A component that declares a material grammar must keep the default default_grammar_type = Discipline.GrammarType.JSON. The material grammar carries the bounds and descriptions of the properties, which a SimpleGrammar (a plain name→type map) cannot represent; only a JSONGrammar can be loaded from a schema file, and only a JSON schema can be read back by load_input_bounds to build the model input space.

    And in the material_grammar_file argument documentation of BaseComponent.__init__ (base_component.py:57-63), where the reader who is about to pass the argument will actually be looking. The class currently has no Args: section; adding one for this argument is the minimum.

    2.4 Correct the tan_oht docstring¶

    Replace the stale sentence at tan_oht.py:112 with a statement of the constraint, so the closest example to the failure explains itself:

        """An Open Hole Tension model based on Tan theory (#open-hole-plate-model-tan-model).

    The ply material properties are declared through ``MATERIAL_GRAMMAR_FILE``,
    which is why this component keeps ``default_grammar_type = "JSONGrammar"``:
    a material grammar cannot be loaded into a ``SimpleGrammar``.
    """

    3. Rejected alternatives¶

    Convert the schema and feed the simple grammar. JSONGrammar.to_simple_grammar() exists (base_grammar.py:449), so update_from_file could load into a scratch JSONGrammar and the converted result be merged into whatever the component uses. Mechanically this works, and that is the problem: the bounds and descriptions are dropped in the conversion (§1.1), load_input_bounds never runs (§1.3), and the model comes out with an infinite input space. It converts a failure that stops the run into a wrong answer that does not. The whole point of passing a material grammar is the bounds; silently discarding them to keep the constructor alive serves nobody.

    Skip the grammar file with a warning, keep only the values. Technically available, per §1.2 — default_input_data is grammar-agnostic, so the component would run with correct nominal values. Same objection, plus a second one: material inputs would also lose grammar validation, so an out-of-range nu12 would flow through untouched. A warning is too quiet for a component that asked for a material contract and got none.

    Both alternatives are variations on "make it work anyway". Given that §1.3 already shows one silent bounds-loss path in the codebase, adding a second is the wrong direction.

    4. Backward compatibility¶

    No public API change; BaseComponent.__init__ keeps its signature.

    The guard of §2.1 fires only when material_grammar_file is supplied and the grammar is non-JSON — a combination that today raises AttributeError at the very next line. No configuration that currently constructs successfully starts failing; the change replaces one exception with a better one.

    The warning of §2.2 fires on a branch that no in-tree model currently reaches (§1.3), so the existing test suite and runnable examples stay quiet. Downstream projects with a non-JSON first component will start seeing it — which is the intent, since those models have had unbounded input spaces all along.

    5. Relation to the material-bounds RFC¶

    rfc_material_property_bounds.md §3.1 proposes a material/grammar consistency check at the same insertion point, base_component.py:77-97. The two compose in one order only:

    if material_grammar_file != "":
    if not isinstance(self.input_grammar, JSONGrammar):   # this RFC, §2.1
        raise TypeError(msg)
    self.input_grammar.update_from_file(material_grammar_file)
    if material is not None:
        _check_material_bounds_consistency(...)            # bounds RFC, §3.1

    The type guard must come first, for two reasons.

    The check is meaningless without a successful load. It compares the bounds held by the grammar against those held by the material. If update_from_file raised, there are no grammar bounds to compare — the check only has meaning inside the branch the guard protects.

    Without the guard it inherits the same obscurity. _check_material_bounds_consistency reaches grammar.schema["properties"] through load_input_bounds (json_grammar_utils.py:62), and SimpleGrammar has no schema. Omitting the guard therefore does not remove the unhelpful error, it moves it one line down — from AttributeError: ... has no attribute 'update_from_file' to AttributeError: ... has no attribute 'schema', this time raised from VIMSEO code rather than GEMSEO.

    That second argument does not cover every grammar type: PydanticGrammar does expose a schema property (pydantic_grammar.py:248-250, returning model_json_schema()), so it would fail at the load rather than at the bounds reading. The first argument covers all three. See §6.2.

    5.1 "Dynamic mode" does not lift the constraint¶

    That RFC's §7.2 aims to delete the grammar file, generating the schema in memory from Material.to_legacy_json_schema. It is tempting to read this as dissolving a constraint phrased as "you need a JSONGrammar to load a file". It does not, because the constraint was never about the file. Both variants sketched in the commented-out block at base_component.py:79-89 are JSONGrammar-only:

    Variant Call Available on
    write a temporary file, read it back update_from_file (json_grammar.py:301) JSONGrammar only
    pass the schema in memory — "the best solution" update_from_schema (json_grammar.py:317) JSONGrammar only

    The constraint is on the destination, not the source. There is still a JSON schema carrying per-property bounds and descriptions, and a name→type map still cannot hold it (§1.1); where the schema came from is irrelevant to what receives it.

    Practical consequence: if dynamic mode is ever implemented, §2.1 survives unchanged — only its error message needs rewording, since it currently names a file path that would no longer exist.

    6. Items to verify before implementation¶

    1. Whether any downstream project overrides default_grammar_type on a component that also receives a material. In-tree there is none (§1.4), so the guard is theoretical here; it is downstream that decides whether this is a bug fix or a documentation change.
    2. Whether PydanticGrammar deserves a distinct message. It is the odd one out on both counts: unlike SimpleGrammar it can express bounds (Field(ge=..., le=...)), and it does expose a schema property (pydantic_grammar.py:248-250, returning model_json_schema()). What it lacks is only the loading half — neither update_from_file nor update_from_schema:
    schema update_from_file update_from_schema
    JSONGrammar yes yes yes
    SimpleGrammar / SimplerGrammar no no no
    PydanticGrammar yes no no

    So telling a Pydantic user "bounds have no representation here" would be false. Either split the message, or word the single message around the loading rather than the representation. 3. Whether the §2.2 warning should instead be an error when the model has a MATERIAL_FILE. A model that declares a material and then reports infinite bounds is arguably always a defect, not a configuration — but this couples two class attributes that are currently independent, and is worth deciding separately. 4. Whether _MATERIAL_GRAMMAR_FILE on IntegratedModel (base_integrated_model.py:203-209) should carry the same statement in its docstring, since that is where model authors declare the file that eventually reaches base_component.py:91.

    7. Test¶

    One test in tests/core/components/test_component.py: a BaseComponent subclass declaring default_grammar_type = "SimpleGrammar" and constructed with material_grammar_file=MATERIAL_LIB_DIR / "Mock_grammar.json" must raise TypeError, with the message matched on the actionable half (default_grammar_type) rather than on the whole string.

    The counterpart — the same subclass with the default grammar type constructing successfully and exposing the material property names in input_grammar.names — pins the rule from the other side and documents that the constraint is about the grammar type alone.
